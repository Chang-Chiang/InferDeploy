## 1. 概念

:question:什么是量化

神经网络模型由网络拓扑图和一系列权重参数组成，量化即是针对其中的权重参数，采用低精度数据类型。

需要补充的是：量化的对象不只是权重，还包括**激活值**（层间中间结果）与**计算过程**（矩阵乘/卷积的输入输出类型）。三者可以同时量化（W8A8，主流），也可以只量化权重（weight-only，见 4.3），这也是部署中很多精度与性能问题的分水岭。

模型推理通过输入数据与权重参数进行计算，从而得到数据结果；模型训练过程中，权重参数通常为 FP32（32 位浮点）类型，在部署推理过程也采用相同精度，则存在内存占用高、计算速度慢 【量化不一定能加快计算速度：比如，针对高精度，TensorRT 可能采用 Tensor Core 计算；针对低精度，TensorRT 可能采用 Cuda Core 计算，Tensor Core 速度快于 Cuda Core，这种场景量化则并未加快计算速度】、功耗大等问题。故可通过量化技术解决这一系列问题，使得原本只能在高端 GPU 上运行的复杂模型能够部署到资源受限的边缘设备上。



:question:为什么训练的时候用高精度，部署的时候用低精度

训练需要高精度，本质是三个环节对数值的**分辨率**和**动态范围**都敏感：

- **参数更新量极小**：单步更新的量级约为 `learning rate × gradient`（1e-5 ~ 1e-3），远小于权重本身（1e-1 量级）。低精度尾数位数不足时，`w + Δw` 会发生"大数吃小数"，Δw 被直接舍入为 0，模型不再更新；
- **梯度动态范围窄**：反向传播中的梯度普遍小于 1e-4，而 FP16 最小正规数约 6e-5，梯度会直接下溢为 0 —— 这正是混合精度训练要引入 loss scaling 与 FP32 master weights 的原因；
- **状态长期累积**：优化器的动量、方差等状态需要跨 step 累加，低精度下误差会持续积累甚至发散。

部署只做前向计算，不需要表示微小增量、也不需要保存梯度与优化器状态，因此低精度可行且划算：

- 神经网络对权重扰动本身具有鲁棒性，量化误差可视为一种加性噪声，只要控制在激活分布的分辨率以内，输出变化通常可接受；
- 推理的瓶颈在内存带宽（权重/激活搬运）与算力峰值，降低位宽可以直接换来收益；
- 显存占用可下降 2~4 倍，使原本只能在高端 GPU 上运行的复杂模型能够部署到资源受限的边缘设备。

> 需要区分两个概念：训练侧的 FP16/BF16 属于**混合精度**（FP16 前向 + FP32 master weights 与累加），部署侧的 FP16/INT8 才是本文讨论的**量化**（权重与激活以低精度存储和计算）。

两点结论：

- **动态范围与精度此消彼长**：位宽固定时，指数位多则可表示范围大但分辨率低。INT8 没有指数位，必须靠 scale 把实数区间"压缩"到 [-128, 127]，所以 INT8 的难点不在数值格式本身，而在**如何为每个张量选到合适的 scale**（见 4.4 校准）；
- **同为 16 bit 的 FP16 与 BF16 并不等价**：BF16 沿用 FP32 的 8 位指数，范围大、精度低，量化/溢出风险小；FP16 精度更高但范围仅 ±65504，激活值溢出风险更大。

## 2. 数学基础

### 2.1 统一的仿射量化模型

量化把连续实数 x 映射到 b bit 整数格点 x_q，反量化再映射回近似值（有损）：

- 量化：`x_q = clamp(round(x / s) + z, q_min, q_max)`
- 反量化：`x = (x_q - z) × s`

其中 s 为缩放因子（scale，实数），z 为零点（zero point，整数），[q_min, q_max] 是目标类型的取值范围（INT8 为 [-128, 127]，UINT8 为 [0, 255]）。本文表格中给出的公式均为 **z = 0 的对称量化**特例。

- **对称量化**：z = 0，`s = max|x| / q_max_abs`。实现简单（无需零点减法），是推理引擎的主流选择；缺点是分布明显偏正（如 ReLU 之后）时会浪费一半格点；
- **非对称量化（MinMax / Affine）**：`s = (x_max - x_min) / (q_max - q_min)`，`z = round(q_min - x_min / s)`。格点利用充分、误差更小；代价是卷积/矩阵乘中零点会引入额外求和项，且多数引擎（含 TensorRT）不支持，实践中以对称量化为主；
- 工程上还常用 **2 的幂次 scale**（s = 2^k），把乘法退化为移位、省去乘算开销（注意：舍入误差本身并不因此消失）。

### 2.2 舍入与截断误差

- `roundWithTiesToEven`（银行家舍入）：.5 一律舍向偶数。若改用 round-half-up 会引入单向偏差，逐层累积后表现为均值漂移；
- 均匀分布假设下，单元素量化误差服从 [-s/2, s/2]，MSE ≈ s²/12；位宽每 +1 bit，误差约减半（信噪比 +6 dB）；
- clip（截断）与 round（舍入）是一对矛盾：scale 取小 → 离群值被削平，截断误差大；scale 取大 → 分辨率下降，舍入误差大。**校准的本质就是在这个权衡上取最优点**；
- 误差逐层累积：激活误差经矩阵乘放大后进入下一层，最终掉点通常由**个别误差最坏的层**决定，而非全局平均误差 —— 这也是需要逐层分析（polygraphy）而非只看端到端指标的原因。

### 2.3 低精度算子的实际计算流程

INT8 推理并不是"INT8 输入算完得到 INT8 输出"，典型 INT8 卷积/GEMM 的数据流：

1. 激活与权重均为 INT8；
2. 乘累加在 **INT32 累加器**中完成（避免溢出，这是 INT8 Tensor Core 的固定行为）；
3. 通过 **requantize**（乘 per-channel 缩放因子 + 右移 + 饱和截断）把 INT32 结果压回 INT8，供下一层使用；
4. 偏置、BatchNorm 等参数在构建期折叠（weight folding）进缩放因子或整数常量，避免运行时反量化。

由此可得一个重要结论：**量化只在整条融合层都能以 INT8 执行时才有收益**。一旦某层不支持低精度，就需要在边界插入 DQ → FP32 计算 → Q，额外的格式转换与带宽开销可能抵消量化收益（见 3.3）。

### 2.4 算例：一个张量的 INT8 对称/非对称量化

取 `x = [0.8, -2.4, 1.6, 0.2]`，则 `max|x| = 2.4`，`x_min = -2.4`，`x_max = 1.6`。

**对称量化（TensorRT 采用）**：

- `s = 2.4 / 127 ≈ 0.01890`
- `x_q = [42, -127, 85, 11]`，反量化 `[0.794, -2.400, 1.607, 0.208]`，最大绝对误差 ≈ 0.0079（≤ s/2）

**非对称量化**：

- `s = (1.6 + 2.4) / 255 ≈ 0.01569`，`z = round(-128 + 2.4/s) = 25`
- `x_q = [76, -128, 127, 38]`，反量化 `[0.800, -2.400, 1.600, 0.204]`，最大绝对误差 ≈ 0.0039

该例中分布明显偏正（负向跨度 2.4，正向跨度 1.6），非对称的 s 更小、分辨率更高，误差约为对称的一半；但每层都要多一次零点减法，这正是 TensorRT 仍采用对称量化的原因。

### 2.5 各精度类型的量化/反量化公式

|         | 量化                                                         | 反量化                          |
| ------- | ------------------------------------------------------------ | ------------------------------- |
| INT8    | xq = quantize (x, s) = roundWithTiesToEven (clip (x/s, -128, 127)) | x = dequantize (xq, s) = xq × s |
| FP8E4M3 | xq = quantize (x, s) = castToFP8 (clip (x/s, -448, 448))     | x = dequantize (xq, s) = xq × s |
| INT4    | xq = quantize (x, s) = roundWithTiesToEven (clip (x/s, -8, 7)) | x = dequantize (xq, s) = xq × s |

## 3. 优缺点

### 3.1 收益

- 提升性能，推理速度、吞吐量提升，源于内存带宽需求的降低和计算单元利用率的提高
- 减少内存占用，权重与激活显存按位宽比例下降（FP32 → INT8 约为 1/4），同显存可跑更大 batch
- 提升功耗效率，单位计算能耗降低，边缘设备受益尤其明显
- 降低部署门槛，使复杂模型能运行在资源受限的设备上

### 3.2 代价

- 精度损失，且损失不均匀：个别层可能掉点严重，而整体指标看起来正常
- 模型兼容性要求，并非所有模型架构都能很好地支持量化（含大量归一化/非线性/归约算子的网络尤其困难）
- 硬件依赖性，某些量化特性（如 Tensor Core 加速）依赖于特定的 GPU 架构
- 校准复杂性，为了获得最佳的量化效果，特别是 INT8 量化，需要精心准备校准数据集并进行复杂的校准过程，这增加了部署的复杂性和时间成本
- 调试成本高，掉点原因可能在校准集分布、scale、单异常层、预处理不一致等多处，定位需要逐层对比工具
- 收益可能倒挂，不支持低精度的层需插入 Q/DQ 转换，小模型 / batch=1 / 强依赖前后处理耗时的场景，量化后反而变慢

### 3.3 收益来源与"量化不一定更快"

量化收益主要来自三处：

1. **带宽需求下降**：推理通常是内存瓶颈型，权重/激活搬运量降为 1/4（FP32 → INT8）；
2. **算力峰值提升**：Tensor Core 上 INT8 吞吐通常为 FP16 的 2 倍、FP32 的 4~8 倍；
3. **吞吐提升**：同显存预算下可用更大 batch，摊薄 kernel launch 与预处理开销。

但量化**不必然**加速（第 1 节已提及）：若 FP32 路径本身已走高精度 Tensor Core，而量化后某些层回退到 CUDA Core 计算，还要额外承担 Q/DQ 格式转换与 requantize 开销，端到端反而变慢。因此**量化后必须实测**，不能默认更快（见第 6 节）。

## 4. TensorRT 量化

### 4.1 量化类型

| 类型 | 是否引入 scale | 是否需校准 | 硬件门槛 | 本项目状态 |
| --- | --- | --- | --- | --- |
| FP16 | 否（纯浮点格式转换） | 否 | 几乎全量 NVIDIA GPU（`platformHasFastFp16()`） | 支持，`Params.m_ePrec = FP16`（`samples/sample.cpp` 默认） |
| INT8 | 是 | 是（激活需统计） | Turing+（`platformHasFastInt8()`） | 支持，显式量化（Q/DQ）为主，legacy calibrator 保留 |
| FP8（E4M3/E5M2） | 是 | 是 | Hopper+（sm_90）/ Blackwell | TRT 10 支持显式 FP8（modelopt），本项目未启用 |
| INT4 | 是（通常需分组量化） | 是 | Hopper+ 且需 TensorRT-LLM / ModelOpt 路径 | 主要面向 LLM 权重量化，本项目未启用 |

补充：

- 严格说 FP16/BF16 属于**精度转换**而非量化（无 scale、无格点映射），但 TensorRT 用同一套 `BuilderFlag` 机制管理，习惯上并入量化讨论；
- BF16（`kBF16`）动态范围与 FP32 相同，是 FP16 溢出场景（激活值范围大）在 Ampere+ 上的替代选择；
- TF32 不需要任何开关，Ampere+ 上 FP32 矩阵乘默认可能已走 TF32。若发现 FP32 引擎结果与训练侧不完全一致，先排查这一点，不要误归因于量化。

### 4.2 量化粒度

- **逐张量量化（Per-tensor quantization）**
  - 使用单个缩放值（标量）来缩放整个张量
  - 计算简单，内存开销小
  - 可能因为张量内数值分布不均而导致精度损失
  - 适用于数值分布相对集中的张量，如经过 BatchNorm 处理后的激活值
- **逐通道量化（Per-channel quantization）**
  - 为每个通道单独计算缩放因子，能够更好地适应通道间数值分布的差异
  - 在保持精度方面通常优于逐张量量化，特别是对于权重张量
- **块量化（Block quantization）**
  - 将张量沿单一维度划分为固定大小的 1D 块，为每个块定义一个缩放因子

TensorRT 显式量化下的实际支持范围：

- **激活**：仅支持 per-tensor（运行时无法按通道统计，且 per-channel 激活需额外归约开销）；
- **权重**：支持 per-tensor 与 per-channel（沿输出通道轴）。卷积核各 filter 间的量级差异大，INT8 下 **per-channel 权重量化几乎是必须的**（modelopt 默认开启），否则精度损失明显；
- **块量化**：主要面向 LLM 权重（如 INT4/FP8 + 128 元素分组），需较新的 TRT 10.x 与对应硬件，CV 模型很少用到。

### 4.3 量化分类

量化可从五个正交维度分类，实际方案是各维度取值的组合。

**(1) 按是否需要训练 —— PTQ vs QAT**

| | PTQ（训练后量化） | QAT（量化感知训练） |
| --- | --- | --- |
| 输入 | 已训练好的 FP32 模型 | 需回到训练流程 |
| 原理 | 用少量校准数据统计激活分布，确定 scale | 训练中插入 fake-quant 节点，前向带量化误差，反向用 STE（直通估计）更新权重 |
| 成本 | 低（分钟级） | 高（需重训，要打通数据与训练管线） |
| 精度上限 | 多数 CV 模型可达 FP32 的 99%+ | 更高，低比特（INT4/FP8）或 PTQ 大幅掉点时才需要 |
| 本项目 | 采用（modelopt PTQ → Q/DQ ONNX） | 未采用 |

**(2) 按量化对象**

- 仅权重量化（weight-only，如 W8A16 / W4A16）：权重压到低位宽，计算时反量化回 FP16 参与运算。收益主要是显存与带宽，几乎不掉点、无需校准激活，是 LLM 场景主流（AWQ/GPTQ）；
- 权重 + 激活量化（W8A8）：真正用上 INT8 算力，收益最大，但激活必须校准，掉点风险也最大 —— CNN 部署的标准形态；
- 仅激活量化：几乎不单独使用（权重分布可离线确定，没有不量化的理由）。

**(3) 按 scale 的产生时机**

- 静态量化（static）：离线校准得到固定 scale，推理时无额外开销，TensorRT 走这条路径；
- 动态量化（dynamic）：运行时按当前张量实际 min/max 计算 scale，免校准、精度更稳，但每层多一次统计开销，主要面向 Transformer/LLM 的激活。

**(4) 按量化信息的注入方式（TensorRT 的两条路径，与 4.4.5 呼应）**

- 隐式量化（implicit calibration）：ONNX 中不含 Q/DQ，构建期由 `IInt8Calibrator` 跑校准集统计 dynamic range。TRT 8.x 的主流方式，**TRT 10.1 起弃用、10.x 后期实现已被移除**；
- 显式量化（explicit quantization / QDQ）：量化信息以 `QuantizeLinear`/`DequantizeLinear` 节点的形式写死在 ONNX 图里，构建器只需尊重图中 Q/DQ 位置，不再需要 calibrator。NVIDIA 官方推荐的 10.x 路径，也是本项目当前路径。

**(5) 按数值格式**

- 定点量化（INT8/INT4）：均匀格点，完全依赖 scale，对离群值敏感；
- 浮点量化（FP8/BF16/FP16）：非均匀格点，天然带指数，动态范围问题弱于定点，但尾数位极少，对分辨率损失仍敏感。

**选型建议（CV 模型 + TensorRT）**：FP16 → INT8 W8A8 静态 PTQ（显式 Q/DQ、对称、权重 per-channel）→ 若掉点不达标，先修校准与敏感层回退（4.5）→ 仍不达标再考虑 QAT。

### 4.4 校准

#### 4.4.1 为什么 INT8 需要校准

权重的 scale 可以直接从权重张量算出（离线、可 per-channel），但**激活值的分布无法从权重推出** —— 它取决于真实输入。校准即是用一小批代表性数据前向推理、逐张量统计激活分布、再据此选定 scale 的过程。

若不做统计而直接按 FP32 的 min/max 映射（naive Max），单个离群值就会把 scale 拉大、把绝大多数正常值压到少数格点上，精度严重损失；反之若截断过狠（Entropy 阈值取太小）则关键极值信息丢失。TensorRT 提供的 5 类校准器正是这组权衡的不同实现（本项目实现前两种，见 `include/core/Calibrator.h`）：

| 校准器 | 统计策略 | 特点 |
| --- | --- | --- |
| `IInt8EntropyCalibrator2` | 最小化量化前后分布的 KL 熵 | 主动截断两端离群值，通用性好，官方默认推荐；对分布尖锐、极值关键的网络会丢信息 |
| `IInt8MinMaxCalibrator` | 取全局 min/max，不做熵截断 | 保留 FP32 极值分布，对离群值敏感；DWConv 较多的架构（YOLOv8）上常能恢复精度 |
| `IInt8EntropyCalibrator` | 旧版 Entropy 实现 | 已不推荐，效果弱于 Calibrator2 |
| `IInt8LegacyCalibrator` | 历史兼容策略 | 仅用于对齐旧版本 engine 的结果 |
| `IInt8Calibrator` | 基类，可自定义 `getBatch` 等 | 可实现 percentile / MSE 等自定义统计逻辑 |

> 上述校准器属于**隐式量化**路径（4.3 第 (4) 类）。显式量化（Q/DQ）下 scale 已写死在 ONNX 图里，构建期不再调用 calibrator，但"用真实分布做统计"这一要求并不因此消失 —— 只是把校准前移到了 modelopt PTQ 阶段（见 4.4.5）。

#### 4.4.2 校准流程（隐式量化路径）

INT8 量化需要校准数据集统计各层激活值的 dynamic range，据此计算缩放因子（scale）。流程：

1. 准备校准数据集（图片路径列表，每行一个路径）；
2. 继承 `nvinfer1::IInt8Calibrator` 系列实现自定义 Calibrator（本项目见 `include/core/Calibrator.h`）；
3. 在 `BuildEngine` 中设置 `kINT8` + `kPREFER_PRECISION_CONSTRAINTS`，并通过 `config->setInt8Calibrator()` 挂载；
4. 构建过程中 Calibrator 逐 batch 读取图片、上传 GPU，TensorRT 在 GPU 上统计 dynamic range；
5. 统计结果写入 calibration table（校准表），下次构建时通过 `readCalibrationCache` 读取，跳过校准过程。

#### 4.4.3 校准集选择

| 项目 | 要求 |
| --- | --- |
| 数量 | 500～1000 张（TensorRT 官方建议），过少会导致 scale 统计不稳定 |
| 分布 | 必须覆盖部署场景的真实输入分布（类别、光照、分辨率等），与训练数据同源不同样本 |
| 预处理 | **必须与真实推理的预处理完全一致**，否则 dynamic range 统计失准（本项目曾因此存在分类/检测预处理不一致的隐患，现已修复） |
| 缓存 | 更换模型、校准器（Entropy ↔ MinMax）或校准集后，**必须删除 calibration table 重新校准** |

本项目现状：

- `calibration/calibration_list.txt`（120 行）为 demo 占位数据（4 张图各重复 30 次），仅能验证流程；
- `calibration/calibration_list_coco.txt`（2000 张 COCO 图片）为正式校准集模板，实际使用时需将路径替换为本机数据集路径；
- 校准表路径按算法区分：`calibration_table_entropy.txt` / `calibration_table_minmax.txt`。

#### 4.4.4 校准器选型（Entropy vs MinMax）

本项目通过 `Params.m_eCalibAlgo` 切换：

- `ENTROPY`（`IInt8EntropyCalibrator2`）：基于 KL 熵最小化，忽略 dynamic range 两端的极值，通用性强，默认推荐；
- `MINMAX`（`IInt8MinMaxCalibrator`）：保留 FP32 极值分布。

参考 tensorrt_starter 7.4 的实测结论：YOLOv8 含大量 DWConv（depthwise conv），各层输出分布差异大，
使用 Entropy 校准会丢失关键极值信息，导致 classness 掉点严重；换用 MinMax 后精度可恢复。
若精度仍不达标，可继续通过 `Params.m_vecFp32Layers` 将敏感层强制回退 FP32
（配合 `kPREFER_PRECISION_CONSTRAINTS`，如 YOLOv8-seg 分割头的 `/model.22/proto/cv3/act/Mul`）。

#### 4.4.5 TensorRT 10+：显式量化（当前环境适用）

legacy calibrator 在 TensorRT 10.1 起被弃用，且在新版 10.x（实测 10.8/10.16）中实现已被移除，
构建时会直接崩溃，**必须改用显式量化（Explicit Quantization）路径**：

1. 用 NVIDIA TensorRT Model Optimizer 对 ONNX 做 PTQ，在图中插入 Q/DQ 节点：

   ```bash
   # 环境: deps/pyenv（pip install nvidia-modelopt[onnx]）
   python data/models/quantize_yolo.py                      # 默认量化 yolov8n-seg.onnx
   python data/models/quantize_yolo.py -i onnx/yolov8n.onnx # 检测模型
   ```

2. 产物为 `<model>-int8.onnx`，直接用它构建引擎即可，构建器检测到 Q/DQ 节点后
   自动跳过 calibrator（见 `TrtBackend::BuildEngine`，`src/core/TrtBackend.cpp`）；
3. `trt-quant-eval` 会自动优先加载 `<model>-int8.onnx` 作为 INT8 侧；
4. 注意：`quantize_yolo.py` 默认用随机张量校准（仅验证流程），
   正式部署应通过 `--calibration-data-path` 传入覆盖部署分布的真实数据，
   否则会出现明显的匹配率/置信度损失（本项目测试环境即如此，详见第 5 节实测）。

显式量化路径的两个易踩点：

- **必须同时允许 FP16**：modelopt 产出的 Q/DQ 模型中部分层/常量为 FP16 类型，未开 `kFP16` 会直接构建失败（本项目已自动处理）；
- **Q/DQ 的位置决定一切**：构建器不再自行决策量化范围，而是尊重图中 Q/DQ 边界。modelopt 默认不动的层（Softmax、LayerNorm、Resize 等）会自动保持高精度，这通常正是我们想要的结果。

### 4.5 逐层精度控制

TensorRT 用 `BuilderFlag` 表达精度约束强度（本项目在 `src/core/TrtBackend.cpp` 中设置）：

- 不设任何 flag（默认 `kBEST_PRECISION`）：构建器自行选择最快的精度组合；
- `kPREFER_PRECISION_CONSTRAINTS`：尽量满足层精度设置，无对应 kernel 时允许回退（**本项目采用**，配合 `kFP16` / `kINT8`）；
- `kOBEY_PRECISION_CONSTRAINTS`：严格禁止回退，找不到对应 kernel 直接构建失败。用于验证"某层是否真的以 INT8 执行"，代价是可能根本构建不出引擎。

**敏感层回退 FP32**：`Params.m_vecFp32Layers` 中列出的层名会被强制 `setPrecision(kFLOAT)` + `setOutputType(0, kFLOAT)`（按层名精确匹配，层名可从 ONNX 图或构建日志取得）。本项目对 YOLOv8-seg 分割头 `/model.22/proto/cv3/act/Mul` 使用该机制。

**天然不会被量化的位置**：模型输入/输出张量（除非显式声明）、Softmax / LayerNorm / Resize / Reduce 等非线性与归约类算子、以及 Q/DQ 未覆盖的分支，通常以 FP32/FP16 执行。掉点排查时优先确认这些边界是否被误量化。

**查看实际层精度**：构建期日志（`PrintNetwork`，已开启 `kDETAILED` profiling verbosity）、`trtexec --verbose`，或用 `polygraphy run --trt --onnxrt` 逐层对比输出误差。

### 4.6 本项目落地清单与常见坑

端到端命令见 5.4。按顺序核对下列检查项：

| # | 检查项 | 说明 / 典型症状 |
| --- | --- | --- |
| 1 | 工作目录必须是 `bin/` | 校准列表、engine、result 均按 `../` 相对路径解析，否则报找不到文件 |
| 2 | 校准预处理 == 推理预处理 | 分类 `GPU_BILINEAR` + ImageNet mean/std；检测/多任务 `GPU_WARP_AFFINE` letterbox + /255。不一致时 dynamic range 失准，表现为 INT8 置信度大幅偏离 |
| 3 | 校准集真实且足量 | 随机张量 / 占位列表只能验证流程，不能用于验收（5.4 的 FAIL 即此因） |
| 4 | 换模型/校准器/校准集要删表重建 | 删除 `calibration_table_entropy.txt` / `calibration_table_minmax.txt`（仅 legacy 隐式路径需要） |
| 5 | 显式量化模型必须允许 FP16 | 见 4.4.5，否则构建失败 |
| 6 | engine 文件名带精度后缀 | `<model>-fp32.engine` / `-fp16.engine` / `-int8.engine`；改了精度却复用旧 engine，会得到"看起来没量化"的结果 |
| 7 | pip 版 TRT 库需 `patchelf --clear-execstack` | 新内核会拒绝加载带 executable stack 标记的 `libnvinfer_builder_resource`，表现为加载即段错误 |
| 8 | 先排除部署链路缺陷再归因量化 | 曾出现输入维度解析错误导致缓冲欠分配，表现为随机崩溃与 0 检出，极易被误判为"量化掉点" |

## 5. 精度评估

### 5.1 评估方式

INT8 相对 FP32 的精度损失，有三种互补的度量方式：

1. **绝对精度（需要标注数据集）**：
   - 分类：ImageNet val 上的 Top-1 / Top-5 Accuracy；
   - 检测/分割：COCO val2017 上的 mAP@0.5:0.95（分割额外看 mask mAP）。
   - 需要接入 COCO/mAP 评估工具链（如 pycocotools、polygraphy），本项目暂未集成；
2. **相对一致性（无需标注）**：以 FP32 引擎输出为基准，同一组图片对比 FP32 与 INT8 输出差异。适合快速回归验证，本项目已实现该方式。
3. **逐层定位（调试用）**：若前两种度量发现掉点、但不知掉在哪一层时，用 polygraphy 逐层 dump 并对比 FP32/INT8 中间张量（如 `polygraphy run model.onnx --trt --onnxrt --atol 0.1 --rtol 0.1 --markers`），找到误差突增的层，再按 4.5 回退。本项目未集成，命令需额外安装 `polygraphy`。

### 5.2 本项目评估工具

`samples/quant_eval.cpp`（编译产物 `bin/trt-quant-eval`，`make quant-eval` 单独构建）：

```bash
# 在 build/bin 目录下运行（需能找到 calibration/ 目录与模型文件）
./trt-quant-eval <cls|det|multi> <onnx_model_path> <image_list.txt 或单张图片路径>
```

指标（以 FP32 为基准）：

| 任务 | 指标 | 含义 |
| --- | --- | --- |
| 分类 | top-1 一致率 | INT8 与 FP32 top-1 类别相同的比例 |
| 分类 | 平均置信度差 | top-1 置信度绝对差均值 |
| 检测/多任务 | 匹配率 | 同类别且 IoU ≥ 0.5 的贪心匹配成功率 |
| 检测/多任务 | 匹配框平均 IoU | 反映框回归精度损失 |
| 检测/多任务 | 平均置信度差 | 匹配框置信度绝对差均值 |

### 5.3 验收线（默认值，可按项目调整）

| 任务 | 验收条件 |
| --- | --- |
| 分类 | top-1 一致率 ≥ 99% 且 平均置信度差 ≤ 0.05 |
| 检测/多任务 | 匹配率 ≥ 95% 且 匹配框平均 IoU ≥ 0.90 且 平均置信度差 ≤ 0.05 |

工具会输出 PASS / FAIL。验收不达标时的排查顺序（参考 tensorrt_starter 7.4）：

1. input/output 附近是否被量化；
2. 多任务模型是否只有部分 task 掉点；
3. 校准集分布、数量是否合适，预处理是否与推理一致；
4. 校准 batch size 是否合适；
5. 更换校准算法（Entropy → MinMax）；
6. 用 `m_vecFp32Layers` 将敏感层回退 FP32；
7. 使用 polygraphy 做逐层对比分析（见 5.1 第 3 种方式）。

排查前先用 4.6 的清单确认不是环境/链路问题（工作目录、旧 engine 复用、占位校准集等），这些症状与"量化掉点"完全同形。

### 5.4 实测记录（RTX 5070 Ti + TensorRT 10.16，yolov8n / yolov8n-seg）

环境说明：RTX 5070 Ti 为 Blackwell（sm_120）架构，要求 TensorRT ≥ 10.8，
项目已从 TRT 8.6.1.6 迁移至 10.16（pip tensorrt-cu12 libs + GitHub 头文件，见 `deps/TensorRT-10.16`）。

端到端流程（工作目录 `bin/`）：

```bash
# 1. 导出 ONNX（含 box-major 转置）
python ../data/models/export_yolo.py -m yolov8n-seg.pt
python ../data/models/export_yolo.py -m yolov8n.pt

# 2. INT8 显式量化（PTQ → Q/DQ）
python ../data/models/quantize_yolo.py
python ../data/models/quantize_yolo.py -i onnx/yolov8n.onnx

# 3. FP16 推理
./trt-infer ../data/models/onnx/yolov8n-seg.onnx ../data/source/crowd.jpg

# 4. FP32/INT8 量化精度评估（自动加载 -int8.onnx）
./trt-quant-eval multi ../data/models/onnx/yolov8n-seg.onnx ../data/source/image_list.txt
./trt-quant-eval det   ../data/models/onnx/yolov8n.onnx   ../data/source/image_list.txt
```

实测结果（5 张测试图，Q/DQ 模型用随机数据校准）：

| 任务 | FP32 框数 | 匹配率 | 匹配框平均 IoU | 置信度差 | 判定 |
| --- | --- | --- | --- | --- | --- |
| MULTITASK | 58 | 60.34% | 0.9392 | 0.2075 | FAIL |
| DETECTION | 59 | 71.19% | 0.9325 | 0.1650 | FAIL |

结论：匹配上的框位置很准（IoU ≈ 0.94），但匹配率/置信度差超出验收线，
根因是 PTQ 使用了随机校准数据，统计到的激活分布与真实输入不符——
这正是第 4.4.3 节强调的校准集质量问题的直接体现。
换用真实数据校准后重测即可回归。

> 复现说明：DETECTION 侧结果稳定（2026-09-17 重跑逐项相同：71.19% / 0.9325 / 0.1650）；
> MULTITASK 侧存在阈值边界的非确定性，2026-09-17 重跑为 58.62% / 0.9394 / 0.2035
> （58 框匹配 34，上表 60.34% 对应匹配 35）。
> 检测任务的完整部署流程、逐图检测结果与可视化对比见
> [目标检测部署流程.md](./目标检测部署流程.md)。

### 5.5 局限性

- 相对一致性评估不等于绝对精度：FP32 与 INT8 可能"一致地错"；上线前建议在有标注的数据集上补测 mAP / Top-1；
- 当前评估基于图片级回归，未覆盖视频流等时序分布漂移场景；
- 默认只跑 5 张测试图（`data/source/image_list.txt`），样本量远不足以下结论，只能验证流程跑通；正式验收至少需要数百张覆盖部署分布的图像。

## 6. 性能与资源评估

精度达标后，还需确认"是否真的更快、更省"（见 3.3，量化不必然加速）。三项指标：

| 指标 | 采集方式 |
| --- | --- |
| 端到端时延 | `bin/trt-infer` 的计时日志：`preprocess(CPU)` / `preprocess(GPU)` / `trt-inference(GPU)`（CUDA event）/ `postprocess(CPU)`；需 warmup 后取多次统计 |
| 吞吐 | batch=1 时量化收益有限；把 engine 建成 batch>1 或用 `trtexec` 压测 FPS |
| 显存 / 产物体积 | `nvidia-smi` 观察峰值显存；对比 `data/models/engine/*.engine` 与 `onnx/*.onnx` 文件大小 |

注意：

- 时延对比必须固定预处理路径（`Params.m_eDevice` 的 CPU / GPU）与输入尺寸；小分辨率输入时，端到端耗时中前后处理占比可能超过网络本身，量化收益会被淹没；
- engine 与 GPU 架构、TensorRT 版本绑定（本项目 `deps/TensorRT-10.16`，sm_120），换卡需重新构建再测；
- 若 INT8 反而变慢，按 3.3 排查是否有大量层回退并插入 Q/DQ（用 `kOBEY_PRECISION_CONSTRAINTS` 或逐层日志确认）。
